# 相关软件与标准：旁注、摘录、锚定与工作区

本文梳理公开产品、研究原型与标准如何实现「在材料上做注、把注再当材料、以及如何存」。重点是意图、可见功能、公开的数据结构、以及它们为何这样取舍。每一节末尾才对照 intro。intro 的定位只作对比用：本地无账号的材料库；侧边挂在选区上、可递归嵌套且不允许交叉，侧边本身是完整宿主；新建 / 复用 / 节选；Electron 横向多列；正文内标记为权威（SoT）；去掉标记即干净正文。

公开网页在撰写时部分能打开、部分超时或被机器人验证拦住。凡未能当场核对的细节，标为「公开资料未在此次核对」，不编造未公开的内部库表。

## LiquidText

站点：[https://www.liquidtext.net/](https://www.liquidtext.net/)

1. **意图。** 把阅读、划线、摘录、观察从「像纸一样」推进到「能看见连接」：笔记彼此相连、并能指回原文。目标用户是合同、案卷、尽调一类需要跨页找事实的专业阅读，而不是写一篇可再挂侧边的探究链。营销语言强调比纸更快、一次读完就能留下可回头的结构。

2. **功能。** 从 PDF 等文档把摘录拖到无限画布；笔记与观察可互相连线；捏合（pinch）把文档不同部分拉到一起看；搜索结果可并排对照上下文。导出公开宣传为 PDF 与 DOCX。LiquidText LIVE 是云订阅：多设备实时同步与备份（[产品页 LIVE 说明](https://www.liquidtext.net/)）。公开材料强调评论/工作区注释**不写回**原 PDF 文件本身。没有公开的「选区上再挂一篇完整宿主、且嵌套不交叉」的 span 树。

3. **数据结构 / 存储。** 厂商未公开内部 schema。从产品行为可推断：工作区是「文档 + 画布上的摘录卡片 + 连接」的项目，权威在应用自己的项目文件/云端，而不是 PDF 内嵌 Annot。LIVE 把项目放到云上。精确字段名、表结构：**公开资料未在此次核对**。

4. **设计理由与取舍。** 画布适合「把事实从页里拽出来并排比较」；不写回 PDF 避免污染源文件、也避开 PDF 注释模型表达不了连接图的问题。代价是互操作弱：离开 LiquidText，连接图不易原样打开。云 LIVE 解决多设备，但把权威从单机文件挪到账号同步。无限画布解决空间，不解决「这段字是另一段字的子论证」这种递归宿主关系。

5. **和 intro 的差。** LiquidText 是摘录到画布并连线，不是选区锚定的递归侧边。intro 的侧边是完整宿主、可再划再挂；LiquidText 的卡片是工作区里的叶子或图节点。intro 无账号、标记在正文里；LiquidText 有云 LIVE，注释不写回 PDF。两者都关心「摘出 + 指回」，但 intro 的树来自嵌套标记，LiquidText 的图来自画布连线。

## MarginNote

站点：[https://www.marginnote.com/](https://www.marginnote.com/)

1. **意图。** 「深读留下痕迹」：高亮、脑图、闪卡同一套学习集，以后还能找回。面向论文综述、医考、法学院案例、语言学习等「读完还要记、还要复习」的场景，而不是把侧边再当成下一层完整文本宿主。

2. **功能。** PDF / EPUB / 网页 / 视频；划线自动成卡片；OCR（公式、表、手写）；卡片与源页双向跳转。十种脑图样式。Wiki 式卡片互链与全局搜索。FSRS 间隔重复。MN 4 有 Immersive Recall。公开社区与二次开发（如 OhMyMN）常见操作：把摘录拖到已有卡片下作子节点，或合并。一张卡片通常对应**一条主摘录**。导出能力在用户口碑里偏弱；PDF 常被拷进应用内部工作区。iCloud 同步；有账号/订阅或买断。平台以 iPad 与 Mac 为主。

3. **数据结构 / 存储。** 商业闭源，无公开库表。行为上：学习集 = 源文档副本 + 卡片（摘录 + 笔记 + 复习状态）+ 脑图父子。权威在 MarginNote 自己的包/iCloud，不是「正文里的嵌套标记」。OhMyMN 等插件操作的是卡片树，不是 span 树。精确 SQLite 字段：**公开资料未在此次核对**。

4. **设计理由与取舍。** 把「划线 → 卡片 → 脑图节点 → 闪卡」做成同一对象的三种面貌，适合应试与文献消化。父子关系是**主题/大纲树**，不是选区嵌套：父卡片不必对应子卡片在原文中的包含关系。拷贝 PDF 换取离线与批注稳定，代价是与外部 PDF 注释不同步、导出困难。FSRS 把产品拉向记忆，而不是拉向论证展开。

5. **和 intro 的差。** 脑图父子 ≠ intro 的选区嵌套（不允许交叉的 span 树）。intro 侧边是宿主，可再挂；MarginNote 卡片以一条摘录为中心，复习调度是一等公民。intro 本地无账号、Electron 多列；MarginNote 是 iPad/Mac + iCloud。intro 的新建/复用/节选是笔记身份问题；MarginNote 更接近「每条划线一张卡，再在脑图里归类」。

## SuperMemo Incremental Reading 与 Extract

入口：[Incremental reading](https://help.supermemo.org/wiki/Incremental_reading)、[Extract](https://help.supermemo.org/wiki/Extract)（此次抓取被 Cloudflare 验证页拦住，细节以既有公开说明与 briefing 为准，字段级页面内容标为未当场核对。）

1. **意图。** 增量阅读：把长文切成可学习的碎片，按间隔重复安排「下一次读哪一块」。Extract 是把选中的一段变成子条目，形成章 → 段 → 句的嵌套摘录链，目的是记忆与消化，不是探究式侧边阅读。

2. **功能。** Windows 上的 SuperMemo 本地库。在文章中选取片段 Extract，生成嵌套的子条目；原条目与摘录之间可跳转。调度是 SRS（SM 系列算法），不是横向多列工作区。增量阅读还有 cloze、postpone 等学习操作。公开 wiki 把 Extract 定义为从父条目切出子条目的操作。

3. **数据结构 / 存储。** SuperMemo 集合是本地知识树：条目（item）有父子、有学习参数、有 HTML/富文本内容。Extract 在结构上是**条目树**，锚点是「从哪篇切出来」，不是 PDF QuadPoints 或 W3C selector。内部文件格式（如 collection 的二进制/XML 变体）随版本变化，**公开资料未在此次核对**具体文件布局。

4. **设计理由与取舍。** 嵌套 extract 让「先读章、再读段、再读句」和复习队列同一套树。取舍是：树的语义是**学习粒度**，不是「这段论证挂在那段原文上、侧边还是完整宿主」。Windows 本地、无现代云账号模型（相对 Reader 类产品），但生态封闭、导出到通用笔记格式弱。不做横向列、不做「复用已有笔记 / 节选大笔记中一段」作为一等操作（extract 默认是切出新条目）。

5. **和 intro 的差。** 嵌套 extract 是最接近 intro「递归」的公开先例之一，但 SuperMemo 的子条目是复习卡片，不是可再当宿主展开的侧边列。intro 禁止交叉、标记在正文；SuperMemo 的权威在条目树与学习数据。intro 要新建/复用/节选与搜索；IR 的默认动作是切出并进入队列。没有 Electron 多列。

## Muse / Allume

现产品：[https://allume.com/](https://allume.com/)（Muse 已改名 Allume）。研究叙事：[Ink & Switch · Muse](https://www.inkandswitch.com/muse/)

1. **意图。** 给「想法尚未成形」的阶段一个工作室：收集素材、空间摆放、墨水与摘录，而不是排版完稿。Ink & Switch 对比物理工作室（乱、混媒介、东西呆在你放的地方）与常见数字工作区（按类型分仓、由计算机排序）。Allume 继续「嵌套白板」：一块板里再放板，想法可以分叉生长。

2. **功能。** 嵌套 boards；卡片可含文字、涂鸦、图、视频、PDF、链接；Inbox 收新材料；PDF 阅读与批注；摘录并保留来源联系（研究文与产品都强调 excerpt + source）。local-first，可同步；Pro 有协作、实时光标。刻意不做复杂画笔、复杂排版、无限缩放旋转。导出板为 PDF/PNG。平台：iPad / iPhone / Mac。

3. **数据结构 / 存储。** 公开原则是 local-first 加同步，不是「打开网站才有数据」。权威是板与卡片的空间图，不是正文 span 标记。内部 CRDT/文件格式 **公开资料未在此次核对**（Ink & Switch 文章讲设计，不给生产库 schema）。

4. **设计理由与取舍。** 空间与嵌套板解决「主题里再开一层主题」；摘录解决「从长 PDF 拉出一句仍指回去」。不做 span 树是因为目标是 ideation 画布，不是在一段字上挂另一篇完整可读宿主。少 chrome、要快、要笔，是针对早期思考的摩擦，不是针对导出干净论文正文。协作是后加的社交层，与早期 local-first 研究原型不完全同一约束。

5. **和 intro 的差。** 嵌套的是**板**，不是选区上的宿主。intro 的树由正文标记的嵌套形成；Allume 的树由空间包含形成。两者都有摘录+源链接，但 intro 还有复用已有笔记、节选范围、以及「去标记 = 干净正文」。intro 是横向列跟当前路径；Allume 是画布。intro 无账号单人库；Allume 有免费档与订阅、可选协作。

## Heptabase

PDF 与划记说明：[https://wiki.heptabase.com/pdf-annotation](https://wiki.heptabase.com/pdf-annotation)

1. **意图。** 用白板做复杂主题的学习与研究：把 PDF、网页、视频、播客变成可拖上白板的卡片，划记变成可摆放的「材料」，再与笔记卡并置、连线。

2. **功能。** PDF 拖入成 PDF 卡；选字划记或 Cmd/Ctrl 框选区域划记；每条划记进入卡片库，成为 **Highlight Card**。可从划记跳回原文位置。划记卡可拖到白板，可 Copy link 后在其他笔记里 embed。另有 Readwise、Zotero 连接，网页 Insight、YouTube 字幕与时间戳、播客转写。云账号产品。

3. **数据结构 / 存储。** 公开描述：卡片库中的对象类型（笔记卡、PDF 卡、划记卡、视频卡等）。划记卡是叶子：指向 PDF 上的一处高亮，本身不是再开放划记的递归宿主。云端存储细节、是否另有 selector 表 **公开资料未在此次核对**。

4. **设计理由与取舍。** 把高亮提升为卡片，才能和白板其他对象平等操作（拖、连、嵌）。代价是「高亮」停止在叶子：不能在划记卡的正文上再划出下一层 Heptabase 式宿主链（笔记卡可以再写，但那是另一张卡，不是选区铆定的侧边）。云与账号换来跨设备与连接器（Zotero/Readwise）。

5. **和 intro 的差。** Highlight Card ≈ 叶子摘录；intro 的侧边 ≈ 完整宿主。Heptabase 的递归发生在白板嵌套/卡片嵌入，不发生在选区 span 树。intro 本地无账号；Heptabase 云。intro 横向列沿锚点打开；Heptabase 主壳是白板。

## Latticework

项目页：[https://www.matthewsiu.com/Latticework](https://www.matthewsiu.com/Latticework)（Matthew Siu & Andy Matuschak，2024）。代码：[https://github.com/Siunami/Latticework](https://github.com/Siunami/Latticework)。相关思考传统可见 [Matuschak notes](https://notes.andymatuschak.org/)。

1. **意图。** 把「在 PDF/材料上的批注」和「在笔记里的自由书写」合成一套增敏（sensemaking）工作流，而不是批注归批注、卡片归卡片。标题即主张：Unifying annotation and freeform text editing。

2. **功能。** 公开页与仓库将其定位为研究/原型（常以 Obsidian 插件形态出现）：页边、反向链接、捕获（capture）与消化（digest）的区分。不是完整商业阅读器。GitHub 星标量级说明它是可运行的原型而非大众产品。页上长文的实现细节若未打开全文：**部分公开资料未在此次核对**。

3. **数据结构 / 存储。** 作为 Obsidian 插件时，权威落在用户库的 Markdown 与插件数据，而不是独立闭源库。具体 frontmatter、块 ID 约定以仓库为准，**字段级未在此次逐文件核对**。

4. **设计理由与取舍。** 站在「批注工具太像高亮叶子、笔记工具又丢掉原文位置」的缝上。用现有 PKM（Obsidian）降低存储发明成本。原型可以激进试交互，但不提供 intro 那种独立 Electron 库与导出披露模型。Matuschak 一系强调可执行笔记、记忆与理解，和「侧边即宿主」只有部分重叠。

5. **和 intro 的差。** Latticework 试统一批注与书写，但仍是插件生态里的页边/反链，不是「选区铆定、侧边为宿主、嵌套不交叉、正文标记为 SoT」的完整产品。intro 自研工作区壳；Latticework 寄生 Obsidian。两者都关心 digest 不只是 highlight。

## Hypothesis

产品：[https://web.hypothes.is/](https://web.hypothes.is/)。锚定：[Fuzzy anchoring](https://web.hypothes.is/blog/fuzzy-anchoring/)（2013）。课堂对比：[Hypothesis vs Perusall](https://web.hypothes.is/hypothesis-perusall-compared/)

1. **意图。** 在**他人的网页/PDF**上做社会性批注：读者没有写原文的权限，所以必须在不改宿主文件的前提下指向任意片段。对话（回复）是一层，不是把回复做成新的完整文档宿主。

2. **功能。** 浏览器/PDF 上选区批注、公开或小组、回复串。锚定策略公开写得很清楚：同时存多种 selector，重挂时按策略降级。与 Perusall 等课堂工具相比，Hypothesis 更偏开放 Web 与标准；Perusall 的多层课堂线程对「多级探究宿主」帮助不大（见对比文）。云账号。

3. **数据结构 / 存储。** 对齐 W3C Web Annotation 思想。Fuzzy anchoring 文列出当时保存的三类：
   - **RangeSelector**：起止 XPath + 元素内偏移（来自 Annotator 传统）；
   - **TextPositionSelector**：全文字符起止；
   - **TextQuoteSelector**：exact + 前后各 32 字符 prefix/suffix。
   重挂顺序：Range → Position → 先上下文再模糊 → 只对 exact 模糊（Bitap / diff-match-patch）。另有 DOM↔字符串双向映射。批注正文与回复存在 Hypothesis 服务端，**不是**写进被注页面。内部 Postgres 表名等 **非公开，不推测**。

4. **设计理由与取舍。** 宿主会改、会有多格式副本，所以不能只信 XPath。多 selector + 模糊匹配换鲁棒，换来歧义（改文后可能挂错）。回复树是**会话**，允许交叉引用讨论，不要求「不交叉的选区树」。云是因为批注必须离开无写权限的文档单独存。

5. **和 intro 的差。** Hypothesis 的权威在侧车批注库 + selector；intro 的权威在宿主正文标记。Hypothesis 回复不是宿主；intro 侧边是宿主。Hypothesis 为对抗网页变动而模糊锚定；intro 第一版以本地稳定文本为主，PDF 保真单列里程碑。Hypothesis 要账号与社交；intro 单人无账号。两者都面对「选区在介质上如何再找到」——这是 intro 结论里也承认的难题。

## Genius

说明：[How Genius Works](https://genius.com/Genius-how-genius-works-annotated)

1. **意图。** 大众协作解释歌词（及扩展文本）：划一段，写注解，经编辑审核成为「官方」Genius Annotation。社会声望（IQ）、upvote、艺术家认证。不是个人探究工作区。

2. **功能。** 高亮一行或数行开始注解；同一注解可通过歌词里的 ID 语法挂到重复歌词（公开问答：URL 里的数字 ID 写入方括号标记，且**不能跨歌曲**）。前后文由歌词行本身提供。无「注解再当完整宿主往下挂探究列」。要账号。

3. **数据结构 / 存储。** 公开可见的是：歌词文本 + 注释放在服务端，歌词里可用 `[text](id)` 一类约定把多处指向同一注解。内部库 **不公开，不编造**。片段锚定是「歌词字符串上的区间」，并靠前后行当人类上下文。

4. **设计理由与取舍。** 社会生产知识需要审核与单一「官方注」，所以注解是叶子 + 讨论，不是递归宿主。跨曲不复用同一注，避免版权与语境错乱。标记写进歌词源，是为了重复副歌——这与 intro「标记在正文」形似，但语义是「多处指向同一社交注解」，不是嵌套侧边树。

5. **和 intro 的差。** Genius 是社交叶子注解；intro 是个人递归宿主。Genius 要账号与编辑；intro 无账号。形似的「正文里出现注的 id」在 Genius 是歌词工程，在 intro 是整棵钉树的 SoT。Genius 不提供新建/复用/节选库内笔记的工作区语义。

## Zotero

产品与 PDF 阅读器：[https://www.zotero.org/](https://www.zotero.org/)、[PDF reader](https://www.zotero.org/support/pdf_reader)。为何注记进库：[annotations in database](https://www.zotero.org/support/kb/annotations_in_database)

1. **意图。** 个人与课题组的文献库：书目、PDF、笔记。阅读器把批注当成 Zotero 一等对象，以便同步、标签、搜索、生成笔记，而不是把 PDF 当唯一真理。

2. **功能。** 内置 PDF 阅读器：高亮、下划线、笔记、图注等。可从批注生成笔记（引用摘录）。可导入 PDF 内嵌注释（导入后从 PDF 移除以免重复）。可导出带内嵌注释的 PDF 副本。可用外部阅读器，但与库内注记不同步。本地库为主，可选 Zotero 同步（含群组）。无账号也能单机用。

3. **数据结构 / 存储。** 公开说明：Zotero 6+ **自己的批注存在 SQLite 数据库**，不写回 PDF。理由包括：同步时只传注记而非整份多 MB 文件；群组避免整文件冲突；可给注记打标签、在库内过滤；标准 PDF Annot **表达不了他们的高级模型**。嵌入式 PDF 注释只读，除非 Import Annotations。库可用标准工具打开；也有 Web API。具体 `itemAnnotations` 等表字段以源码/社区文档为准，此处不编造列名。

4. **设计理由与取舍。** 文献管理要搜索与同步，PDF 文件是糟糕的多用户数据库。写回 PDF 会整文件冲突（他们写明 Zotero 5 时代的痛）。取舍：互操作靠导出，日常权威在 SQLite。批注仍是**叶子**（一条高亮 + 一条评论），生成的笔记是扁平摘录笔记，不是递归侧边宿主。

5. **和 intro 的差。** 两者都偏本地库、都可以无强制社交账号（Zotero 同步可选）。Zotero 的对象是书目项与扁平批注；intro 的对象是带嵌套钉的宿主与侧边宿主。Zotero SoT 在 DB；intro SoT 在正文标记。Zotero 生成笔记是摘录汇编；intro 的节选是指向（篇 + 范围）而非默认复制。没有横向探究列。

## Obsidian：PDF++ 与块引用

PDF++ 链接格式：[https://ryotaushio.github.io/obsidian-pdf-plus/link-copy-formats.html](https://ryotaushio.github.io/obsidian-pdf-plus/link-copy-formats.html)。Obsidian 核心：[块引用](https://help.obsidian.md/Linking+notes+and+files/Blocks)（`^id`）、嵌入 `![[]]`。

1. **意图。** 把仓库做成 Markdown 知识库；PDF 是附件。PDF++ 增强「从 PDF 选区拷出链到笔记」。块引用让笔记之间复用**块**，不是任意 UTF-8 闭包选区上的递归侧边。

2. **功能。** 原生 Copy as quote：引用块 + `[[pdf#选区]]` 一类链接。PDF++ 用模板自定义 display text 与整段剪贴板（`{{text}}`、`{{page}}`、`{{pageLabel}}` 等）。反向高亮：笔记里的链可以在 PDF 上标出对应处。Markdown 侧：段落/列表/标题可加 `^block-id`，他处 `[[note#^id]]` 或嵌入。PDF 文件与 MD 文件**分开**。

3. **数据结构 / 存储。** 权威分裂：PDF 二进制 vs 笔记 Markdown。选区链接的精确编码（页、偏移、quad）由 Obsidian/PDF++ 约定，存在 MD 链接字符串里，不是 PDF Annot。块 ID 是笔记文件内的标记，只锚块边界，不锚任意 span，也不能表达「块内再嵌套一块侧边宿主」除非用户手工再拆文件。

4. **设计理由与取舍。** 兼容纯文本库与 Git；PDF 保持原文件。代价是双文件、选区鲁棒性依赖阅读器实现、没有单一「去标记得干净 PDF+笔记」的 inverse。块引用解决复用，但复用单元是编辑器块，不是选区树。

5. **和 intro 的差。** intro 一种宿主一种标记 SoT；Obsidian 是 PDF∥MD。`^id` 是块复用，不是嵌套 span。`![[]]` 是嵌入叶子或块，嵌入目标通常不能再在嵌入视图里当 intro 意义上的宿主往下挂列。intro 的横向列是产品壳；Obsidian 是分栏插件生态。

## Logseq PDF

1. **意图。** 大纲数据库：一切皆块。PDF 批注要变成可查询的块，才能和双向链接、查询同一套模型。

2. **功能。** 社区与文档中的常见行为：PDF 高亮生成 annotation 块；属性如 `hls__` 页面、`ls-type:: annotation` 等（具体键名随版本/插件变化）。可从块跳回 PDF。主界面是大纲缩进，不是横向宿主列。

3. **数据结构 / 存储。** Markdown/Org 文件 + 块 UUID。批注是带类型属性的块，指向 PDF 位置。精确属性集合 **随版本，公开资料未在此次逐版核对**。权威在图数据库式块存储，不在 PDF 文件。

4. **设计理由与取舍。** 与 Zotero 类似：高级查询需要离开 PDF。大纲缩进表达层级，那是块树，不是原文选区包含树。PDF 与图分裂。

5. **和 intro 的差。** Logseq 块树 ≠ intro 选区树。annotation 块是叶子。intro 标记嵌套用栈解析；Logseq 用块引用与属性。都有「跳回 PDF」，但 intro 要把侧边当宿主。

## Acrobat 与 PDF 注释（ISO 32000）

Acrobat 是 PDF 注释的事实参考实现。标准：[ISO 32000](https://www.iso.org/standard/63534.html)（PDF 2.0 等；全文需购标准，下列为业界公开共识）。

1. **意图。** 在文件内保存印刷品式批注：高亮、便签、图章、墨迹，换阅读器仍在。权威在文件字节里，便于归档与打印。

2. **功能。** 高亮、下划线、删除线、文本框、自由笔、回复（reply 树，会话而非宿主）。注释可导出 FDF/XFDF。不提供「注释本体再作为完整文档往右开一列」。

3. **数据结构 / 存储。** 页面上的 Annot 字典：`Rect`、`QuadPoints`（高亮四边形）、`Contents`、`IRT`（回复）等。**QuadPoints** 定义与 Acrobat 常见顶点顺序不一致，pdf.js 等会规范化——这是 PDF 高亮互操作的经典坑。标准 Annot **表达不了** Zotero 式标签、Heptabase 式白板卡、intro 式嵌套宿主。故 Zotero 把高级注记放在 DB（见上节公开 KB）。

4. **设计理由与取舍。** 文件自包含、无账号、适合司法与出版。取舍：模型是 1990 年代页上矩形，不是 span 树；回复是注释上的注释，不是新宿主；跨页、回流文本、扫描件 OCR 都脆弱。

5. **和 intro 的差。** 都可能「无账号、东西在文件里」。PDF Annot 是叶子几何；intro 是正文标记树。Acrobat 回复 ≠ intro 侧边宿主。intro 明确第一版可不做完 PDF 铆点；Acrobat 的整个存在就是 PDF 铆点。

## Kindle、Apple Books 与同类阅读器

1. **意图。** 消费级电子书：划线、书内笔记、跨设备同步。目标是个人高亮库，不是研究工作区。

2. **功能。** 叶子高亮 + 短注；Kindle 可进 [Kindle Notebook](https://read.amazon.com/notebook) / 导出；Apple Books 笔记随 iCloud 账号。Google Scholar PDF Reader 等是页边叶子评论。高亮一般不能再当一本「书」往下挂。

3. **数据结构 / 存储。** 账号侧数据库 + 专有格式（AZW/KFX、Apple 图书库）。位置常用位置码/EPUB CFI，不是用户可见的嵌套标记。内部表 **不公开，不编造**。DRM 书无法当 intro 式本地可剥离标记的宿主。

4. **设计理由与取舍。** 同步与版权要求权威在商店账号。叶子模型对「读完划线」足够。不开放任意深度宿主是因为产品不是写作 IDE。

5. **和 intro 的差。** 账号与 DRM vs intro 本地库。叶子 vs 递归宿主。无新建/复用/节选工作区语义。无横向列。

## Readwise Reader

产品：[https://readwise.io/read](https://readwise.io/read)

1. **意图。** 把「稍后读」做成以高亮为一等公民的阅读壳，再把高亮喂给 Readwise 复习与导出到 Obsidian/Notion 等。替代 Pocket 一类inbox。

5. **和 intro 的差。** 必须账号 vs intro 无账号。叶子高亮 vs 侧边宿主。导出 MD 是扁平摘录流；intro 导出要能再打开工作区或带开合的 HTML。Reader 有多列阅读体验的部分，但不是沿锚点长出的探究列。

## Docear

站点：[https://docear.org/](https://docear.org/)

1. **意图。** 学术文献套件：用一张脑图同时组织 PDF、PDF 内注记、以及论文草稿。开源、本地、宣称不 lock-in（BibTeX、XML），注册非必须。

2. **功能。** 监视文件夹中的 PDF；把 PDF 里的高亮/书签/注释导入脑图节点；可在图里写草稿并带参考文献。推荐系统等在线服务后来不稳（站点更新曾声明 online services down）。依赖 **外部 PDF 阅读器写下的注释**，自己不是现代 PDF 引擎。

3. **数据结构 / 存储。** Freeplane 脑图 XML + JabRef/BibTeX。注记节点来自解析 PDF 注释，不是自研 span 标记。项目年久，格式以那些开源组件为准。

4. **设计理由与取舍。** 一张图看见「文献—摘录—大纲」是 2010 年代初的完整答案。取舍：PDF 注释质量取决于外部工具；软件老化；脑图父子仍是主题树。本地无账号与 intro 相近。

5. **和 intro 的差。** 都是本地库、都把摘录放进可导航结构。Docear 的结构是 mindmap，锚在 PDF Annot 上；intro 是选区标记树 + 侧边宿主。Docear 不提供横向列与复用/节选一等语义，也不把侧边当完整宿主。

## Tufte CSS 旁注

文档：[https://edwardtufte.github.io/tufte-css/](https://edwardtufte.github.io/tufte-css/)（亦见 [GitHub tufte-css](https://github.com/edwardtufte/tufte-css)）

1. **意图。** 把 Tufte 印刷旁注搬到网页：**作者排版**时把补充说明放在栏外，读者不必跳到页脚。不是阅读器里对任意选区挂注。

2. **功能。** `sidenote` / `marginnote`：正文中插入 label、checkbox、`span.sidenote`。宽屏在边栏，窄屏用 checkbox 展开。编号旁注 vs 无编号边注。这是 CSS 与 HTML 约定，不是批注系统。

3. **数据结构 / 存储。** 旁注内容就在 HTML 源码里，和正文同一文件。没有独立 selector。嵌套旁注不是模型的一部分；交叉、重叠由作者手工避免版面碰撞，没有「交叉即损坏」的解析器。

4. **设计理由与取舍。** 印刷传统：次要信息靠近所指句。Web 上用隐藏+toggle 模拟边栏。作者必须在源码里放好旁注，读者不能对任意选区新建一棵侧边。清掉旁注标签会删掉旁注内容（内容在 span 里），不是 intro 那种「去掉铆点标记、正文一字不改」。

5. **和 intro 的差。** 词都叫 sidenote，机制相反：Tufte 是作者排版；intro 是读者/写者对选区铆钉、侧边为宿主、可递归。intro 的 HTML 导出可能视觉上像边栏（结论中的读者壳 B），但数据模型不是 Tufte CSS。不要把两者当成同一功能。

## CriticMarkup

工具包：[https://github.com/CriticMarkup/CriticMarkup-toolkit](https://github.com/CriticMarkup/CriticMarkup-toolkit)

1. **意图。** 在纯文本/Markdown 里用内联语法做审稿：插入、删除、替换、高亮、评论，并能 **accept 成干净文本**。

2. **功能。** 如 `{==高亮==}{>>评论<<}` 等。处理器可生成干净稿或 HTML 审阅稿。已知痛点：跨块（跨段落）困难；与 Markdown/HTML 分隔符碰撞。

3. **数据结构 / 存储。** 权威即文件里的括号语法。无独立 DB。嵌套与重叠没有严格「不交叉」的产品级解析承诺，冲突靠作者避免。

4. **设计理由与取舍。** 审稿要能进 Git diff。取舍是语法噪音、与 MD 冲突、难跨结构边界。评论附加在高亮上，评论本身不是新宿主文档。

5. **和 intro 的差。** 「可 strip 成干净正文」与 intro 的 inverse 同类。CriticMarkup 是线性审稿操作，不是递归侧边树，也不支持交叉检测为损坏。intro 标记带稳定 id、解析出钉树；CriticMarkup 是编辑动作流。

## mdcomments

仓库：[https://github.com/raveeshbhalla/mdcomments](https://github.com/raveeshbhalla/mdcomments)

1. **意图。** 给 Markdown 一个开放批注格式，便于人与 AI 协作：规格 + CLI + 网页编辑器。

2. **功能。** 公开定位：用 **零宽锚点** + **侧车 JSON** 存评论。**故意不把选区包起来**，从而不能嵌套、不能重叠——与 intro 相反。适合「在点上挂评论」而非「这段是子宿主」。

3. **数据结构 / 存储。** 正文几乎不变（零宽字符）+ 旁路 JSON。权威分裂。仓库星标很少，属早期规格。JSON schema 细节以仓库为准，**未在此次展开每一字段**。

4. **设计理由与取舍。** 不包裹选区，是为了避免破坏 Markdown 解析、避免嵌套冲突。这是明确的设计选择，不是疏忽。代价正是无法表达 intro 的嵌套不交叉 span 树。

5. **和 intro 的差。** 几乎是对照实验：mdcomments 禁止包裹与嵌套；intro 以包裹/标记嵌套为 SoT。都想 strip/干净阅读，但 mdcomments 靠锚点可忽略，intro 靠删全部约定标记且正文不变。

## W3C Web Annotation

规范：[Annotation Data Model](https://www.w3.org/TR/annotation-model/)（此次全文抓取超时，选择器名称以规范通行表述与 Hypothesis 实践为准；条款编号未当场核对。）

1. **意图。** 让批注成为可互换的 Web 资源：谁（body）注了什么（target），target 用 selector 描述，不修改被注资源。

2. **功能。** 数据模型支持多种 target：整页、片段。文本常用 **TextQuoteSelector**、**TextPositionSelector**；结构用 **RangeSelector** 等。还有 CSS selector、XPath、数据位置等。动机是互操作与归档，不是规定 UI 必须递归宿主。

3. **数据结构 / 存储。** JSON-LD 图：`Annotation`、`body`、`target`、`selector` 组合。存储位置由实现决定（Hypothesis 云、本地文件等）。规范不规定 SQLite 表。

4. **设计理由与取舍。** 分离 body 与 target，才能注只读 Web。多 selector 为鲁棒性（与 Hypothesis 实践一致）。不建模「body 又是一篇带 selector 树的完整宿主」为必选；实现可以嵌套 annotation，但语义仍是图上的注解，不是 intro 的正文标记树。

5. **和 intro 的差。** W3C 是侧车选择器；intro 是宿主内标记。W3C 允许描述任意 Web 目标；intro 第一版宿主是本地文本/以后 PDF。intro 的不交叉嵌套是产品不变量；W3C 不强制该不变量。intro 若将来导出互操作，可能**引用**这些 selector 概念，但不把侧车图当 SoT（结论为做法 A：标记在正文）。

## Roam、Tana 的块复用（简述）

Roam Research、Tana（以及 Scrintal 的卡片）把知识切成**块/节点**，块可被多处引用、嵌入。

1. **意图。** 网络化大纲：一处写、多处链，图比文件夹更适合联想。Tana 加强类型与字段；Roam 强调双向链接与块引用。

2. **功能。** 块引用 / transclusion；缩进树；查询。不是在 PDF/长文的任意字符闭包上挂侧边。复用单元是编辑器给出的块边界。

3. **数据结构 / 存储。** 云图数据库（Roam）；Tana 云工作区。块 ID 全局。内部 schema **不公开，不编造**。

4. **设计理由与取舍。** 块边界清晰才能引用稳定。任意 span 没有自然 ID，除非另做锚定层——这些产品选择不做那一层，把粒度停在块。

5. **和 intro 的差。** intro 的复用包括「整篇笔记」和「一篇中的一段范围（节选）」；Roam/Tana 复用块。intro 嵌套来自选区包含；Roam 嵌套来自大纲缩进。都可能形成有向图（intro 复用后多父锚点）。intro 无账号；Roam/Tana 要账号。

## Annoteca（Obsidian）

仓库：[https://github.com/ckelsoe/obsidian-annoteca](https://github.com/ckelsoe/obsidian-annoteca)

1. **意图。** 在长 Markdown 里做分类的内联反馈：给人与 AI 都能读的锚定高亮 + **线程式评论**。

2. **功能。** HTML 标记写在正文里；线程评论；可剥成干净文本。公开描述强调 review threads，不是「侧边再当完整宿主」。

3. **数据结构 / 存储。** 正文内 HTML 标记 + 评论数据（插件侧）。星标很少，属小插件。精确标记语法以仓库为准，**未逐行核对源码**。

4. **设计理由与取舍。** 标记在正文，才能和 MD 一起版本管理，也能 strip。线程是审稿会话。不把评论做成可再划选的第二篇文档，避免和 Obsidian 编辑器抢「什么是笔记」。

5. **和 intro 的差。** 「正文标记 + 可 strip」与 intro 很像。差在语义：Annoteca 是审稿线程；intro 是递归宿主侧边、不允许交叉、横向列、新建/复用/节选。不要把线程深度当成 intro 的树深度。

## 标准与局部方案

下面这些不够单独成章，但说明「相邻问题」都被单独解决过，只是组合不同。

1. **PDF QuadPoints 与实现分歧。** ISO 32000 规定高亮四边形；Acrobat 顶点顺序常与字面规范不一致；pdf.js 等会归一化。任何把 PDF 当宿主的系统（Zotero、Hypothesis PDF、将来的 intro M5）都要面对这层几何，而不是假设「选区 = 字符串下标」。Zotero 公开选择把高级模型放在 DB，因为标准 Annot 不够用。

2. **课堂与社交划线。** [Kami](https://www.kamiapp.com/)：PDF 课堂批注与作业。Perusall：强制社交阅读，线程为课程设计，[与 Hypothesis 的对比](https://web.hypothes.is/hypothesis-perusall-compared/) 说明多层讨论 ≠ 多层宿主。 [Glasp](https://glasp.co/)：社交高亮叶子。都要账号，叶子模型。

3. **并排笔记本。** [Flexcil](https://www.flexcil.com/)：PDF 与笔记本并排，笔记不是挂在选区上的递归宿主。macOS **SideNotes** 一类：贴在屏幕边缘的便签，与文档选区无关。

4. **空间超文本与老文献库。** [Tinderbox](http://eastgate.com/Tinderbox/)：空间超文本、地图与复合笔记，权威在自身文档，不是 PDF span 树。[Qiqqa](https://jimmejardine.github.io/qiqqa-open-source-website/)：开源化的 PDF 文献库与批注，偏管理与主题，不是递归侧边。[reMarkable](https://remarkable.com/)：纸感墨水批注，文件在设备/云，叶子笔迹。[Scholarcy](https://www.scholarcy.com/)：自动摘要闪卡，生成叶子，不挂探究链。

5. **Scrintal。** 白板 + 卡片，节点复用接近 Heptabase/Roam，不是任意 span。

6. **局部方案对照表（概念层，非内部库）。**

   | 方案 | 锚在哪 | 注的身份 | 权威 | 嵌套 |
   | --- | --- | --- | --- | --- |
   | PDF Annot | 页几何 | 叶子评论 | 文件 | 回复树 |
   | W3C / Hypothesis | selector | 叶子 + 会话 | 侧车 | 讨论嵌套 |
   | Zotero DB | 库内注记 | 叶子，可生成笔记 | SQLite | 无 span 树 |
   | 脑图（MN/Docear） | 卡片/节点 | 摘录卡 | 应用包 | 主题父子 |
   | 画布（LT/Allume/Hepta） | 卡片位置 | 摘录或板 | 项目/云 | 空间包含 |
   | MD 块（Obsidian/Logseq/Roam） | 块 ID | 块 | 文件/图 | 大纲 |
   | CriticMarkup | 内联语法 | 审稿动作 | 同一文件 | 弱 |
   | mdcomments | 零宽点 | 点评论 | 正文+JSON | 故意禁止 |
   | Tufte CSS | 作者插入点 | 排版旁注 | HTML | 无产品树 |
   | SuperMemo Extract | 条目 | 学习条目 | 集合树 | 学习粒度嵌套 |
   | intro（对照） | 正文标记 | 侧边即宿主 | 标记 SoT | 选区树，不交叉 |

## 总结

1. **摘录并指回原文**是成熟功能：LiquidText、MarginNote、Heptabase、Reader、Zotero、Docear、Muse/Allume 都做。intro 不声称发明高亮。

2. **嵌套**在别处是主题树、学习条目树、白板包含或讨论回复，几乎都不是「选区包含且禁止交叉」的 span 树。SuperMemo Extract 的嵌套最像递归切分，但语义是 SRS 条目，不是探究侧边宿主。

3. **侧边即完整宿主、可再划再挂**，加上横向列沿路径展开，没有作为组合出现在上述产品的公开模型里。画布产品用空间冒充「再一层」，卡片仍是叶子或板。

4. **权威放哪**分成几派：文件内 PDF Annot；侧车 selector（W3C/Hypothesis）；应用 DB（Zotero、多数云阅读器）；正文内语法（CriticMarkup、Annoteca、Genius 歌词 ID）；正文几乎不动 + JSON（mdcomments）。intro 选择正文标记为 SoT，并要求 strip 后正文不变——最接近 CriticMarkup/Annoteca 的 inverse，但树语义不同。

5. **本地无账号库**：Zotero、Docear、SuperMemo、Allume 的 local-first 各沾一点；同时满足「无账号 + 递归侧边宿主 + 新建/复用/节选 + Electron 多列」的公开组合仍缺。Zotero 最近本地也最近叶子。

6. **复用**：块工具（Roam/Tana/Obsidian）复用块；Genius 复用同一注解到重复歌词；intro 要整篇复用与范围节选（指向而非默认复制）。公开产品很少把「节选 = 某篇 + 范围」当一等、且节选目标仍是宿主。

7. **PDF 铆点**是公认难题（Hypothesis 模糊锚定、QuadPoints 混乱、Zotero 放弃写回 PDF）。intro 把 PDF 单列里程碑，与这些公开教训一致。

8. **Tufte「旁注」是排版词**，不要和 intro 的选区侧边混淆。

9. **mdcomments 故意不能嵌套**，可当作 intro 标记设计的反面教材：包裹选区才能嵌套，不包裹才能避开 MD 冲突——这是真取舍，不是功能多少的问题。

10. **写作时网络**：LiquidText、MarginNote、Zotero KB、PDF++、Heptabase wiki、Hypothesis fuzzy、Allume、Ink & Switch Muse、Readwise、Docear、Tufte CSS、Genius、Latticework 首页、Annoteca/mdcomments/CriticMarkup 仓库页已抓取。SuperMemo wiki 与 W3C 规范全文此次未打开，相关句已标明。未根据未公开内部数据库编造表结构。
