# Ask Codex：从选区直接生成 Side

方案日期：2026-09-08。状态：用户已选定 App Server 路线，右键入口及自动 side 已接入；实际范围和验证见 [`app/ai/README.md`](../../app/ai/README.md)。以下保留设计提案。当时尚未实现的全文检索等不属于这份提案里的已完成功能。这次没有改正式 library。

## 1. 建议

让 intro 成为一个有原文、有精确选区的 Codex 学习客户端：选中不懂的地方，右键 Ask Codex，解释直接长在原文旁边。用户不用整理提示词、截屏、复制页码，再把回答搬回来。

推荐技术路径：**Electron 主进程启动官方 Codex App Server，通过 stdio 通信；intro 提供有限的原文读取工具，最终由 intro 自己保存 side。**

这条路线保留 Codex 主动查上下文的能力，同时利用 intro 已有的文本、公式和 PDF 锚点。最值得做好的部分是“它知道你问的是哪里，并能回到书里查明白”。

## 2. 接入路径与证据

官方 App Server 面向嵌入式产品客户端，提供会话和流式事件。stdio 是默认传输方式；当前本机 CLI 仍将 app-server 命令标为实验性，动态工具接口也有实验性开关，因此应锁定经过验证的运行时版本。采用它可以避免模拟桌面点击或自行维护模型服务协议。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

Codex 官方支持 ChatGPT 登录和 API key 两种认证；前者使用账户对应的订阅权益，后者单独按 API 计费。方案使用官方登录流程，不自行复制、解析或转交用户的认证文件。具体可用模型及额度以登录账户为准。[官方认证说明](https://learn.chatgpt.com/docs/auth)

| 路径 | 对本项目的判断 |
| --- | --- |
| 官方 App Server | 首选。适合由 intro 管理交互、请求状态和 side 会话。 |
| Codex TypeScript SDK / `codex exec` | 适合先验证一次“给上下文、拿结果”的闭环；可作降级适配器。交互细节仍需 intro 补齐。 |
| OpenAI API | 可作为以后独立的付费接口选项；不能把 ChatGPT 订阅当 API 余额。 |
| Codex 订阅反代 | 已有实现，但 intro 没有必须转换成 Claude Code 协议的需求；维护转换层和认证细节的收益有限。 |
| 操作正在运行的 Codex 桌面窗口 | 不选。窗口焦点、会话选择和 UI 改动都会影响自动化可靠性。 |

SDK 支持程序化创建和恢复线程；非交互 CLI 提供 JSON 事件及结构化最终输出。它们是可用的简化入口，而不是必须先搭建的另一套系统。[SDK](https://learn.chatgpt.com/docs/codex-sdk)、[非交互 CLI](https://learn.chatgpt.com/docs/non-interactive-mode)

### Tibo 所说的反代

找到了代理项目的 [Codex 接入文档](https://claude-code-proxy.raine.dev/providers/codex/)，该页引用并链接了 [Tibo 原帖](https://x.com/thsottiaux/status/2075830097488249060)，转述其欢迎在 Claude Code 中使用 Codex，包含 “We don’t discriminate on the harness.”。本次直接访问 X 返回 403，不能把这次调研写成已独立核验原帖全文。

项目文档也说明它转换协议并处理订阅认证。这证明有实际技术路线，但转述本身不足以概括为“一切反代用法均获允许”。对于 intro，官方嵌入接口和官方个人登录已提供更直接的依据，无需把设计建立在这句话的宽泛解读上。

这里接入的是 intro 自己管理的 Codex 会话。不要假定它会自动继承当前 Codex 桌面聊天的全部历史、记忆，或一定出现在桌面会话列表中。

## 3. 用户实际怎么用

以读 Wilmott 的方差推导为例：

1. 在 PDF 框选第二项，或在 Rendered 公式里选中某一项，右键 **Ask Codex**。
2. 默认问题是“结合原文解释这里，展开必要的推导”；可直接发送，也可输入“为什么要减这一项？”。
3. 原位置旁出现一个临时 side，显示“正在读取本页”“正在查找前文定义”等实际进度，有取消按钮。用户可以继续翻页。
4. Codex 先看选区及所在公式；如果符号定义不清，向 intro 请求前文相关页。
5. 回答完成后，自动保存为普通 side。公式正常渲染，引用能回到实际读过的来源位置；用户可以编辑、Pin、继续给它挂 side。

生成中无需反复确认；点击 Ask Codex 就包含生成并保存该回答的意图。首次连接说明选区及按需读取的上下文会发给 Codex 服务。无网络时仍可正常阅读和写普通笔记。

第一版先显示真实进度，拿到完整回答后再渲染 Markdown，避免半截 LaTeX 不断闪烁。逐字流式正文不是第一版门槛。

## 4. 上下文比提示词更重要

### 文本与公式

点击菜单时立即捕获宿主稳定 ID、原文版本、选区范围、选中文字和前后文。数学选区额外带上所选项对应的 TeX 和完整所在公式，不能把 KaTeX 屏幕文字拼接结果作为唯一输入。

初始上下文包含当前段落、相邻段落和标题。默认要求沿用教材变量，区分原文结论和补充推导；无法确定符号含义时先查定义。

### PDF

当前 `pdf-view.ts` 的选区主要是页码和矩形坐标；这足够挂 side，但还不够让模型理解内容。需要增加 PDF 上下文读取器：

- 同时提供选区图像、所在页图像及可提取的页面文字。公式和扫描页以图像核对，避免文本提取丢失上下标、分数线。
- 明确区分 PDF 文件中的第几页与书上印刷页码；取不到页标签时只标 PDF 页序。
- 按需渲染页面，不依赖当前屏幕 canvas。现有 PDF 视图会卸载远离视口的页，用户翻页后截图来源不能随之消失。
- 不默认上传整本 1401 页书。先给选中页，再按问题读取附近页或搜索定义。

PDF.js 已提供页面访问、文字提取及渲染能力；intro 需要补的是业务封装与选区坐标到图像的转换。[PDF.js 页面 API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html)

### 让 Codex 主动查原文

由 intro 提供三个窄工具，参数使用文档 ID 和页码，而非任意文件路径：

| 工具（拟定） | 返回 |
| --- | --- |
| `read_context` | 指定选区周围的段落、公式、标题，以及来源 ID |
| `read_pdf_page` | 指定页的文字、按需图像、页序和来源 ID |
| `search_document` | 当前文档关键词匹配位置及短上下文 |

工具层优先用本地 MCP；官方支持 stdio MCP 服务及工具白名单。它与 App Server 分工不同：前者供模型读书，后者让 intro 驱动会话。[官方 MCP 文档](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)

第一版检索用按需缓存的页面文字和关键词搜索即可，不先建向量数据库。可先设“初始一页、额外最多六页”的可调预算；这是产品初值，需用实际题目检验，不是模型的能力上限。预算不够时明说依据不足，允许用户继续。

工具只读当前请求绑定的文档。引擎使用独立配置，避免继承用户开发环境的其他 MCP、指令或写权限；禁用与学习无关的 shell、文件修改和外部搜索。必须验证实际配置能执行这些限制，不能只靠提示词；单纯设置 read-only 并不等于限制能读取的文件范围。若无法可靠关闭其他读取渠道，首版退回由 intro 预取上下文的受限模式。

## 5. 回答如何可靠地变成 side

模型只生成内容，例如标题、Markdown 和已读来源 ID。路径、笔记 ID、铆点和坐标由 intro 决定。引用 ID 必须能对应工具实际返回的内容；生成正文不能伪造 intro 的内部铆点语法。

请求开始时保留不可变快照：请求 ID、原 library、宿主 ID、原文版本、选区及提问。完成时不能再读取“当前选区”或“当前打开的库”作为保存目标。

| 生成期间发生的变化 | 处理 |
| --- | --- |
| PDF 翻页、缩放 | 按原 PDF 宿主和原坐标挂接，与当前视口无关。 |
| 文本未变 | 按快照范围自动保存。 |
| 文本已编辑 | 首版保留回答草稿并提示重新定位，不猜测附着位置。后续可复用经过验证的编辑映射。 |
| 宿主删除、library 切换或关闭 | 保留待处理回答，不自动写进另一个库。 |
| 取消、断网、额度不足 | 结束临时状态，允许重试；不遗留空白正式 side。 |
| 重复完成事件、重试或崩溃恢复 | 相同请求 ID 最多提交一次，避免重复笔记。 |

现有 `hangSide` / `hangPdfSide` 会先创建笔记再挂接，不能直接视为一个事务。新增 AI 提交入口应先校验，再以可恢复的写入记录完成“正文 + 挂接”；失败保留可恢复内容，不能成功写了其中一半就宣告完成。这是自动保存需要补齐的可靠性工作。

正式结果仍是现有 `.intro.md` side，PDF 继续用现有侧车锚点，原 PDF 不变。请求日志、模型会话 ID 等先放应用配置中，按库和 side 标识关联，不在第一版扩展正文格式。复制 library 后回答仍能读；跨机器继续同一 AI 会话暂不保证，登录信息也不放 U 盘库中。

## 7. 实施顺序与停止点

**先验证接入（已完成最小探针）。** 2026-09-08 实测找到 Codex CLI 0.153.4，使用已有官方 ChatGPT 登录，在临时目录完成文字 + MCP 上下文读取、图像输入、取消，以及回答的现有渲染器验证。此前调研时 PATH 未找到的情况已更新。当前结果证明接入可用，不代表右键保存闭环或完整权限隔离已通过验收。

**然后只做学习闭环。** 支持文本/公式选区和 PDF 框选、按需读原文、自动生成普通 side。用几道实际类型的推导题评估是否引用正确上下文、解释是否沿用原变量，而不是只测接口返回成功。

**发布前检查失败路径和旧库。** 覆盖生成时编辑原文、翻页、切库、删除宿主、取消、超额、重试、重复事件和重开；在合成库或副本验证原文、标题、ID、既有关系及 PDF 字节保持正确。人工验收由用户进行。

闭环能稳定帮助读书就停止扩范围。向量检索、全库问答、公开服务、多模型调度和复杂 AI 管理面板均不作为这一版门槛。

## 8. 为什么这样设计

用户最耗精力的是把阅读现场搬到聊天窗口，再把解释搬回来。原生选区、按需读书和自动挂接一次消掉这两段工作。

官方 Codex 运行时承担模型连接；intro 掌握原文和位置、控制保存。这样生成能力可以升级，已经积累的笔记仍然独立可读。第一版的成功标准很具体：**读到不懂的一项，问一下，得到有出处的推导，然后接着读。**
